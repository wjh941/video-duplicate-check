# 算法选型笔记 — 为什么是 pHash + dHash、LSH 分桶与 CLIP 融合

> 本文档记录 video-duplicate-check 在感知哈希查重链路上的关键算法决策：
> **为什么用双哈希而不是单哈希、LSH 分桶的参数怎么定、CLIP 语义特征如何与感知哈希融合**。
> 所有数字要么来自代码中的默认值（标注了出处），要么来自本文§3 的可复现实验。

代码位置：`video_dedup/hasher.py`（哈希提取）、`video_dedup/compare.py`（相似度与 LSH）、
`video_dedup/grouper.py`（分组）、`label_verify.py`（标注验证的特征融合）。

## 1. 为什么是 pHash + dHash 双哈希，而不是单哈希

### 1.1 两种哈希看的是画面的不同侧面

工具对每一抽帧先统一缩放为 32×32 灰度图（`hasher._extract_hashes_single`），
然后计算两个 64-bit 哈希（`HASH_SIZE = 8`）：

| 哈希 | 原理 | 擅长捕捉 | 弱点 |
|------|------|----------|------|
| **pHash**（DCT 离散余弦变换哈希） | 对 32×32 取 DCT，保留左上 8×8 低频系数，按中位数二值化 | 画面整体结构、亮度分布、色块布局 | 对局部细纹理不敏感；两幅"结构相同但细节不同"的图可能距离很小 |
| **dHash**（差值哈希） | 相邻像素梯度比较（每行 8 个比较 × 8 行） | 局部明暗梯度、边缘走向 | 对整体亮度/对比度的全局变化更敏感，抗噪性弱于 pHash |

单看任何一方都有系统性盲区。实际数据里最常见的两类"假阴性"恰好互补：

- **转码/换封装的同一视频**：分辨率、码率变了，但画面结构（pHash）几乎不变，
  dHash 会因缩放插值引入少量梯度抖动 → pHash 权重高时判相似 ✓
- **同机位、同构图、但主体换了**（例如固定监控机位前后两段不同事件）：
  低频结构几乎一样（pHash 距离很小），但主体边缘/纹理差异会被 dHash 部分捕捉 →
  dHash 有权重时判不相似 ✓，减少"把不同事件误判为重复"的风险

### 1.2 融合公式与默认权重

`compare.compute_similarity` 的加权融合：

```
similarity = (w_p × sim_pHash + w_d × sim_dHash) / (w_p + w_d)
默认 w_p = 0.7, w_d = 0.3        （config.ini [weights] 段可改）
```

**为什么 pHash 拿 0.7 的大头**：查重工具的核心诉求是"同一内容的不同副本"
（转码、重封装、剪辑首尾）必须聚到一起，pHash 对这类变换最稳定；
dHash 的 0.3 是一个"否决票"式的修正项——它足以把"结构相似但梯度分布不同"的对
拉低到阈值之下，又不至于否决真正的重复。

帧级相似度采用**最近邻匹配**（`_hash_list_similarity`）：对 A 的每一帧，
在 B 的帧哈希列表里找最小汉明距离，再对帧取平均。
这样两段视频抽帧起点略有偏移（常见于剪辑首尾）时依然能对上。

### 1.3 双哈希之外的两道防线

阈值边界上还各有一层保护（都是 v2.x 实战修出来的）：

1. **时长预筛**（`compare.compute_similarity`）：两段视频时长差超过 20% 直接判 0，
   不进入哈希比对。哈希只看画面，不看时间——10 秒和 30 秒的素材即使画面像也不是重复。
2. **音频哈希惩罚**（可选 `--audio-check`，FFmpeg 抽取）：**仅当双方都有音频**且音频
   相似度 < 0.3 时，对画面相似度乘 0.8 的惩罚系数。任意一方无音频/静音不扣分——
   否则"画面完全一致、仅一路无声音"的重复会被误杀。

### 1.4 诚实的边界

pHash/dHash 是**画面相似度**的筛选手段，不是内容鉴定：

- 同机位不同事件的"结构撞车"（pHash 都很小）要靠分组约束（§2.3）和人工复核兜底；
- 高频纹理差异（细条纹换方向）在 64-bit 低频哈希下天然不可见。
  测试里专门有一条断言了这个现象：`tests/test_hashing.py` 的低频图案距离(≈18 bit)
  远大于高频条纹的距离 —— 这也是抽帧缩放到 32×32 后信息损失的直接体现。

## 2. LSH 分桶：参数怎么定

### 2.1 问题：全量两两比对是 O(n²)

n=2000 时两两比对约 200 万次相似度计算。LSH（局部敏感哈希）的思路：
**只让"可能相似"的对进入精确比对**。

### 2.2 为什么不能用「哈希值取模分桶」（v2.6 之前的教训）

直觉做法是把 64-bit pHash 整数对桶数取模（`hash % B`）。**这与汉明距离无关**：
两个只差 1 bit 的近邻哈希取模后几乎必然落入不同桶——真实重复被直接漏掉
（这是比慢更严重的错误：漏报）。v2.6 改为 **multi-band LSH**：

```
把 64 bit 切成 4 个 band × 16 bit；
每个 band 的值单独取模分桶，桶键 = (band_idx, band_value % bucket_count)；
两个视频只要在任意一个 band 上同桶，就成为候选对。
```

原理：近邻哈希的差异数据集中分布在少数 band 里，其余 band 完全相同；
"并集同桶"保证差异不大的对几乎总能被召回。

（`compare._build_lsh_buckets`；`find_similar_pairs` 中 n>50 且
`--lsh-buckets`>0 时启用，n≤50 直接全量两两——小库不值得冒召回风险。）

### 2.3 实验：召回率 vs 桶数

**实验设置**：随机 64-bit 哈希对，人为翻转 k 个比特模拟"相似度衰减"，
N=30 个哈希、200 次试验，统计该对是否被 multi-band 分桶召回为候选：

| 翻转位数 | buckets=32 召回率 | buckets=128 召回率 |
|---:|---:|---:|
| 1  | 100% | 100% |
| 2  | 100% | 100% |
| 4  | 100% | 99.5% |
| 8  | 93.0% | 91.5% |
| 16 | 66.0% | 47.5% |

**成本端**（候选对数量 / 全量对数量，随机哈希、N=2000、4 band）：

| bucket_count | 候选对占比 | 对比全量 |
|---:|---:|---:|
| 16 | 22.8% | 省约 77% |
| 32（默认） | 12.0% | 省约 88% |
| 64 | 6.1% | 省约 94% |

**结论（这就是默认参数的由来）**：

1. **band 数是召回的主力**，bucket_count 在真实重复的典型距离上（pHash ≤ 8 bit）
   几乎不影响召回（93%+），因此把默认桶数定为中庸的 32；
2. bucket_count 只调节成本：32 桶时随机数据下候选集只有全量的 ~12%，
   而真正的重复对（差异 ≤ 8 bit）召回率 ≥ 93%；
3. 距离超过 16 bit 的"弱相似"对召回率明显下降——这是**有意的取舍**：
   这类对即使比对也大多落在阈值（默认 0.7 ≈ 距离 19 bit）边缘，
   漏掉它们换取 88% 的比对量节省是划算的。需要极限召回时，
   关掉 LSH（小库自动走全量）或调低 `--threshold` 即可。

> 复现脚本思路：随机 64-bit 整数对 + 按位翻转 + `video_dedup.compare._build_lsh_buckets`
> 建桶 + 检查两哈希是否共享桶。CI 中的
> `tests/test_lsh.py::test_lsh_recall_on_dedup_pair_large_n` 是它的 60 视频缩微版。

## 3. CLIP 语义特征怎么融进来

### 3.1 分层：感知哈希管"像不像"，CLIP 管"是什么"

CLIP（`ai_semantic.py`，可选依赖）解决感知哈希原理上无法回答的问题：

- 这段视频是"街道行走"还是"犬只训练"？→ 场景/物体/行为零样本分类
- 这批素材适不适合做训练集？→ 数据集用途判定
- neg 样本里是否混入了目标行为？→ `label_verify --verify-neg`

### 3.2 融合点一：label_verify 的相似度判定

预标注一致性验证（`label_verify.hash_similarity` / `motion_similarity`）中，
特征 = 三路信号加权：

```
帧哈希 pHash+dHash（权重 0.6，与主程序同算法）
+ 运动能量（帧间差分，权重 0.4）—— 近似"行为强度"
+ CLIP 图像嵌入（可选）      —— 语义层兜底
```

权重的逻辑：**验证"标注一致性"时，行为比外观更重要**。同标签（如"行走"）
但不同街道的视频，帧哈希相似度天然偏低（预期现象，文档和报告都会提示），
此时以运动能量为主判断；固定机位场景（`--preset surveillance`）再叠加
前景差分哈希（多帧中值估计背景，只对前景差异区域哈希），显著提升区分度。

判定规则：组内平均相似度低于阈值 / 显著偏离标签均值 / 与其他标签更相似
（跨标签吸引力，同时给出建议标签）/ neg 样本被 CLIP 判含目标行为。

### 3.3 融合点二：主查重流程的语义联动

扫描时（`--semantic`）CLIP 嵌入（`semantic_emb`）随哈希一起写入缓存，
供语义聚类（K-Means，`--cluster-semantic`）、数据集导出、语义检索复用。
语义结果**不改变**重复判定本身——查重的相似度仍是纯感知哈希；
语义是叠加在查重结果之上的另一层视图，两层各自可独立复现。

### 3.4 Fallback 链（工程上的妥协）

AI 依赖是可选的，任何一环缺失都要优雅降级：

1. **导入探测**：`cli._ai_probe()` 用 `importlib.util.find_spec` 毫秒级探测
   ai_semantic/torch/open_clip 是否安装，不触发 torch 导入（约 8-10s）；
2. **延迟加载**：真正的 `import ai_semantic` 推迟到第一个 CLIP 调用
   （`cli._ai_mod()`）——纯哈希路径（version/--help/普通扫描）启动 < 0.5s；
3. **运行时降级**：未安装 → 提示并跳过语义功能，纯哈希查重完全不受影响；
   CLIP 权重下载失败 → 自动回退 hf-mirror 镜像重试（label_verify）。

### 3.5 阈值速查

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `--threshold` | 0.7 | 融合相似度 ≥ 该值判为重复（0.7 ≈ 汉明距离 19/64） |
| `--fast` | 阈值 0.85，5 帧 | 快速粗筛：更少帧 + 更高阈值 |
| 时长预筛 | 差异 > 20% 判 0 | 哈希前的廉价过滤 |
| 音频惩罚 | 双方有音频且 < 0.3 时 ×0.8 | 可选 `--audio-check` |
| LSH 启用 | n > 50 | 小库全量两两，不冒召回风险 |
| `--lsh-buckets` | 32 | 见 §2.3 实验 |
| 语义聚类 `--cluster-thresh` | 0.5 | CLIP 嵌入的聚类松紧 |

## 4. 测试如何锁住这些行为

`tests/` 目录（141 个用例，OpenCV 现场合成视频，不依赖真实素材）：

- `test_hashing.py` — 哈希的确定性、亮度鲁棒性、32×32 缩放不变性、缓存命中
- `test_lsh.py` — band 结构、1 bit 差异仍为候选、n>50 时重复对不被漏掉（召回回归）
- `test_similarity.py` — 融合公式、权重生效、音频惩罚触发条件、阈值边界精确值
- `test_grouper.py` — complete-linkage 拆分传递链、四种保留策略
- `test_cleanup.py` — 计划校验/执行/SHA-256 恢复/过期清理全流程
- `test_label_verify.py` — 四种预标注来源识别、一致性判定文案
- `test_end_to_end.py` — 进程内跑通 main()：退出码契约 0/1/2/3 与 summary JSON schema

其中 `test_lsh.py` 的召回回归测试与 `test_similarity.py` 的阈值边界测试，
分别是 §2、§1 中所有数值结论的"可执行版本"——算法文档与测试互为佐证。
